### OpenCode

O `apps/web` ainda não usava Tailwind: os estilos estavam em CSS Modules. Instalei
Tailwind CSS v4 com o plugin `@tailwindcss/vite` e migrei os componentes para
classes utilitárias, aplicando as regras pedidas.

#### Tema e paleta

A paleta do projeto foi declarada no `@theme` de
`apps/web/src/styles/global.css`: `canvas`, `surface`, `surface-soft`, `ink`,
`muted`, `accent`, `accent-hover`, `accent-ink`, `field`, `field-hover`,
`field-ink`, `banner`, `edge` e `focus`. Nenhum hexadecimal ficou fora do tema.

#### Tamanhos de fonte

Os tamanhos foram arredondados para a escala padrão do Tailwind:

| Antes | Token |
| --- | --- |
| 12,5 px | `text-xs` |
| 15 px | `text-sm` |
| 16 px | `text-base` |
| 18 px | `text-lg` |
| 22 px | `text-xl` |
| 31 px | `text-3xl` |

Os valores de 15 e 22 px ficavam entre dois tokens; escolhi o menor para manter a
hierarquia compacta. Também removi os `*.module.css`, substituídos por classes no
JSX, e mantive as medidas específicas do layout (alturas, `padding` e breakpoints)
como utilitários.

#### Configuração e documentação

- `apps/web/vite.config.js` passou a registrar `tailwindcss()`.
- `apps/web/src/styles/global.css` contém apenas o import do Tailwind, o `@theme`

- `AGENTS.md` e `apps/web/README.md` foram atualizados com a convenção de usar os
  tokens de tamanho e a paleta do tema, sem hexadecimais ou tamanhos arbitrários.

#### Verificação

- Layout conferido em Chrome headless em 1920×1300, 768×1600 e 390×1500, nas

### OpenCode

Configurei duas camadas de testes de acessibilidade, sem alterar nenhum componente
(como pedido, só o diagnóstico).

#### O que foi adicionado

**1. Vitest + axe-core (jsdom) — feedback rápido**

- `apps/web/src/test/a11y.js`: helper que roda o axe apenas com as tags WCAG
  2.0/2.1/2.2 níveis A + AA (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`,
  `wcag22a`, `wcag22aa`). Falhas são impressas com regra, impacto, URL e seletor
  do elemento.
- Testes por página: `LoginPage.a11y.test.jsx` e `RegisterPage.a11y.test.jsx`.
- Contraste fica desligado nessa camada porque o jsdom não calcula layout/cores.

**2. Playwright + @axe-core/playwright — navegador real**

- `apps/web/playwright.config.js`: sobe o Vite e roda em Chromium desktop + Pixel 7.
- `apps/web/e2e/a11y.spec.js` cobre, para `/login` e `/cadastro`:
  - axe com as mesmas tags WCAG 2.2 AA (aqui incluindo contraste 1.4.3 e target
    size 2.5.8);
  - título descritivo por rota (2.4.2);
  - reflow a 320 CSS px sem rolagem horizontal (1.4.10).

#### Comandos

| Objetivo | Comando |
| --- | --- |
| Todos os testes de a11y (jsdom + navegador) | `pnpm test:a11y` |
| Só axe no jsdom (rápido) | `pnpm web test:a11y:dom` |
| Só axe no navegador | `pnpm web test:a11y:e2e` |
| Suíte normal (inclui os testes a11y de jsdom) | `pnpm test` |

Em uma máquina nova é preciso instalar o navegador uma vez:
`pnpm web exec playwright install chromium`.

#### Resultado da execução

- `pnpm test:a11y`: 2 testes jsdom + 12 no navegador, todos passando.
- 0 violações WCAG 2.2 AA encontradas em `/login` e `/cadastro`, no desktop e no
  mobile.
- Reflow em 320 px e títulos por rota também passaram.
- `pnpm test` (web + API) e `pnpm web lint` continuam verdes.

Ou seja: os testes automatizados não levantaram problemas no estado atual — a
base está limpa. O valor aqui é a rede de proteção para regressões e o roteiro do
que ainda precisa de verificação.

#### O que o automatizado não cobre

O axe pega uma parte dos critérios (roles, labels, ARIA, contraste, landmarks,
headings, target size). Ainda exigem revisão manual: ordem e visibilidade de foco,
navegação só por teclado, leitor de tela, qualidade dos textos alternativos,
mensagens de erro/sugestões (3.3.1/3.3.3), espaçamento de texto (1.4.12) e
critérios cognitivos.

Também não mexi em `AGENTS.md`, `README.md` nem nos componentes, porque havia uma
migração para Tailwind em andamento em paralelo no working tree. Nenhum commit
foi feito.
