## O que aconteceu com o `pnpm dev:api`

O comando literal falha porque o **Device Guard bloqueia o `pnpm.exe`** — inclusive a cópia que o próprio pnpm baixa em `<diretório-local-do-usuário>/pnpm/.tools/pnpm/12.18.0`. O script raiz ainda tem um problema extra: ele chama `pnpm` por dentro (`pnpm --filter api start:dev`), então mesmo rodando o pnpm via Node o segundo `pnpm` cai no `.exe` bloqueado.

**Solução aplicada:** baixei a distribuição JS do pnpm 10.18.3 via `npm pack` (não usa o exe) para `<diretório-temporário>/opencode/pnpmjs` e executei diretamente o comando que o script executa:

```powershell
node "<diretório-temporário>/opencode/pnpmjs/package/bin/pnpm.cjs" --filter api start:dev
```

Saída confirmada:

```
> api@0.0.1 start:dev ...\apps\api
> nest start --watch
Found 0 errors. Watching for file changes.
Nest application successfully started
```

## Para resolver de forma definitiva

| Opção | Como |
|---|---|
| Liberar o binário (melhor) | Pedir ao suporte/TI para permitir `pnpm.exe` no Device Guard |
| pnpm JS no PATH | `npm i -g pnpm@10.18.3` e garantir que o diretório global do npm venha antes dos shims do fnm |
| Scripts sem pnpm aninhado | Trocar `dev:api`/`dev:web` por chamadas diretas a `nest`/`vite` via `node`, eliminando o `pnpm` recursivo |

Se quiser, eu ajusto o `package.json` com scripts `dev:web:node` / `dev:api:node` (ou substituo os atuais) para você não depender do binário bloqueado.
